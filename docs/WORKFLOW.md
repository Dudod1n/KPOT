# Порядок работы в GitHub

Документ описывает оформление задач, веток, коммитов и pull request.
Правила ревью описаны в [REVIEW.md](../REVIEW.md), выпуск — в [RELEASING.md](RELEASING.md).

## Задачи

Работа ведётся через Issues.

| Тип | Метка | Заголовок |
| --- | --- | --- |
| Ошибка | `bug` | Что происходит не так |
| Возможность | `enhancement` | Что получит пользователь |
| Документация | `documentation` | Что уточнить или добавить |
| Исправления по ревью | `bug` | `Исправления по ревью PR #N, раунд K` |

Оформление:

- Заголовок — одна фраза на русском, без префикса типа и без точки в конце,
  например «Туннель D не переподключается после сна».
- Описание ошибки и предложения заполняется по шаблону из
  [.github/ISSUE_TEMPLATE](../.github/ISSUE_TEMPLATE).
  Ошибка: «Что произошло», «Как воспроизвести», «Ожидаемый результат», «Готово, когда»,
  «Окружение», «Журнал или скриншот». Предложение: «Какую задачу нужно решить»,
  «Предлагаемое поведение», «Готово, когда», «Возможные альтернативы».
- У задачи по документации шаблона нет. Её разделы: «Что уточнить или добавить»
  и «Готово, когда».
- В разделе «Готово, когда» указывается проверяемое условие, по которому задачу
  можно закрыть.
- Одна задача — одна проблема. Несколько связанных проблем оформляются подзадачами
  (sub-issues) общей задачи. Исключение — задача на исправления по ревью: она
  собирает замечания одного раунда.
- Метка типа обязательна. Шаблон ставит свою метку только при создании задачи
  в веб-интерфейсе; при создании через API, `gh` или GitHub MCP метку указывают явно.
- Автор с правами записи ставит метку области при создании задачи,
  см. [Области](#области).
- Перед публикацией удалите из журналов и скриншотов пароли, токены, закрытые ключи
  и личные адреса серверов.
- Связь задачи с PR и её закрытие описаны в разделе [Pull request](#pull-request),
  с коммитом без PR — в разделе [Коммиты](#коммиты).

Задача на исправления создаётся одна на раунд ревью и оформляется как подзадача
(sub-issue) исходной задачи. Если у PR нет исходной задачи, как у PR выпуска,
она создаётся без родителя. В ней указаны PR, проверенные BASE и HEAD полными SHA
и список подтверждённых замечаний P0/P1 с файлом, строкой и сценарием. Раздел
«Готово, когда»: все перечисленные замечания исправлены и проверены на новом HEAD.
Замечания P2 попадают в отдельную задачу только по решению сопровождающего.

### Области

Метка области показывает, где будет исправление, а не где проявилась проблема.
Автор с правами записи ставит её при создании задачи, в остальных случаях — тот,
кто разбирает задачу. Шаблоны задач её не ставят, а автор без прав triage поставить
её не может. После разбора у задачи одна метка типа и одна метка области. Если
задача затрагивает несколько областей, ставится основная; если основную выбрать
нельзя, задачу делят на подзадачи.

Область определяется по таблице: побеждает самая длинная строка, с которой
начинается путь файла. Файл, не подошедший ни под одну строку, относится
к `area:process`. Тесты внутри `src/`, `relay/` и `proto/` относятся к области
своей директории; `tests/` в корне относится к `area:ci`.

| Метка | Пути |
| --- | --- |
| `area:client` | `src/`, `assets/`, `build.rs`, `scripts/build_icons.py`, `Cargo.toml`, `Cargo.lock`, `examples/`, `docs/USAGE.md` |
| `area:relay` | `relay/`, `proto/` |
| `area:release` | `.github/workflows/rust-release.yml`, `scripts/package_release.py`, `scripts/collect_licenses.py`, `scripts/fetch_windivert.py`, `licenses/`, `docs/RELEASING.md` |
| `area:ci` | `.github/workflows/`, `scripts/`, `tests/`, `requirements-test.txt` |
| `area:process` | всё остальное |

`area:release` перечисляет отдельные файлы, потому что выпуск делит директории с CI.

Исключения:

- Задаче «Исправления по ревью» ставится область исходной задачи; если исходной
  задачи нет — область, к которой относится больше всего замечаний. Такую задачу
  на подзадачи не делят.
- Родительская задача метку области не получает: области ставятся подзадачам.

Метки области крупнее области в коммитах (`apps`, `udp`, `ssh`); подробности
остаются в коммитах. Фильтр по двум меткам, например `label:bug label:"area:release"`,
показывает ошибки одной области.

## Ветки

- Имя: `<тип>/<номер задачи>-<кратко-латиницей>`, например `fix/42-ipv6-reject`.
  Тип — один из типов коммитов, кроме `release`. Без задачи номер опускается.
- Вся работа идёт в `dev`. В `main` изменения попадают только через PR `dev → main`
  при подготовке выпуска.
- Изменения идут через ветку от `dev` и PR в `dev`: код, сборка, CI, документация
  и правила. Участник без права записи открывает PR в `dev` из форка.
- Прямо в `dev`, без ветки и PR, коммитит только сопровождающий: правки документации
  и правил и коммит выпуска. К правилам относятся шаблоны задач и PR
  и [CODEOWNERS](../.github/CODEOWNERS); файлы `.github/workflows` относятся к CI.

## Коммиты

Формат: `<тип>(<область>): <описание>`.

- Типы: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`, `ci`, `chore`, `release`.
- Область — модуль или подсистема: `apps`, `udp`, `relay`, `ui`, `ssh`, `review` и т. п.
  Область можно опустить, если изменение не относится к одной подсистеме.
- Описание на русском, со строчной буквы, без точки в конце; описывает результат,
  а не процесс.
- Коммит выпуска: `release: X.Y.Z`. Он меняет версию в `Cargo.toml`, `Cargo.lock`
  и `CHANGELOG.md` по [RELEASING.md](RELEASING.md).
- Коммит без PR ссылается на задачу строкой `Refs #N` в теле сообщения. Задачу
  закрывают вручную после push в `dev`.

Авторство коммитов агентов задаётся по [AGENTS.md](../AGENTS.md).

## Pull request

- Заголовок обычного PR — в формате коммита: `fix(apps): отклонять IPv6 сразу, если сервер его не открывает`.
- Заголовок PR выпуска: `Выпуск X.Y.Z: <главное изменение>`.
- Описание заполняется по [шаблону](../.github/PULL_REQUEST_TEMPLATE.md): Изменение,
  Проверка, Риск, Ревью, Откат, Связанные задачи.
- В разделе «Связанные задачи» обязательна строка `Closes #N`, если задача есть.
  GitHub закрывает задачу по этой строке только для PR в `main`; после слияния
  в `dev` задачу закрывают вручную.
- Один PR — одна задача. PR выпуска объединяет все изменения выпуска.
- PR открывается черновиком. Перевод в «Ready for review» означает, что автор
  выполнил проверки и просит ревью.

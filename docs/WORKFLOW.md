# Порядок работы в GitHub

Документ описывает задачи, ветки, коммиты, pull request и цикл «ревью → исправление → повторное ревью».
Правила самого ревью описаны в [REVIEW.md](../REVIEW.md), выпуск — в [RELEASING.md](RELEASING.md).

Цикл ревью выполняют три workflow из `.github/workflows`:

| Файл | Когда запускается | Что делает |
| --- | --- | --- |
| `claude-review.yml` | PR переведён в «Ready for review»; после исправлений; вручную по номеру PR | Раунд ревью, итоговый комментарий, метки, задача на исправления |
| `claude-fix.yml` | Метка `fix:approved` на задаче на исправления | Исправляет замечания в ветке PR и запускает следующий раунд |
| `task-close.yml` | PR слит в `dev` | Закрывает задачу из `Closes #N` и снимает метки статуса |

Для запуска агента в настройках репозитория нужен один из секретов:
`ANTHROPIC_API_KEY` или `CLAUDE_CODE_OAUTH_TOKEN`. `claude-fix.yml` запускается
по событию задачи, поэтому работает только после попадания в `main`.

## Роли

| Роль | Кто | Что делает |
| --- | --- | --- |
| Сопровождающий | Владелец из [CODEOWNERS](../.github/CODEOWNERS) | Берёт задачи в работу, подтверждает исправления, сливает PR, публикует релиз |
| Автор | Человек или агент | Ведёт ветку и PR, исправляет замечания |
| Ревьюер | Агент, не участвовавший в написании изменения | Проводит раунд ревью по REVIEW.md и публикует итог |

Агент запускается только действием сопровождающего: переводом PR в «Ready for review»
или меткой `fix:approved`. Те же действия других участников и PR из форков
автоматику не запускают.

## Задачи

Работа ведётся через Issues. Доска Project не используется; состояние задачи хранится в метках.

| Тип | Метка | Заголовок |
| --- | --- | --- |
| Ошибка | `bug` | Что происходит не так, одной фразой |
| Возможность | `enhancement` | Что получит пользователь |
| Документация | `documentation` | Что уточнить или добавить |
| Исправления по ревью | `review-fix` | `Исправления по ревью PR #N, раунд K` |

Задача на исправления создаётся одна на раунд ревью и оформляется как подзадача
(sub-issue) исходной задачи. В ней указаны PR, проверенные BASE и HEAD полными SHA
и список подтверждённых замечаний P0/P1 с файлом, строкой и сценарием.
Замечания P2 попадают в отдельную задачу только по решению сопровождающего.

## Ветки

- Имя: `<тип>/<номер задачи>-<кратко-латиницей>`, например `fix/42-ipv6-reject`.
  Без задачи номер опускается.
- Обычные ветки создаются от `dev`, PR направляется в `dev`.
- В `main` изменения попадают только через PR `dev → main` при выпуске.

## Коммиты

Формат: `<тип>(<область>): <описание>`.

- Типы: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`, `ci`, `chore`, `release`.
- Область — модуль или подсистема: `apps`, `udp`, `relay`, `ui`, `ssh`, `review` и т. п.
  Область можно опустить, если изменение не относится к одной подсистеме.
- Описание на русском, со строчной буквы, без точки в конце; описывает результат,
  а не процесс.
- Коммит выпуска: `release: X.Y.Z`.

Авторство коммитов агентов задаётся по [AGENTS.md](../AGENTS.md).

## Pull request

- Заголовок обычного PR — в формате коммита: `fix(apps): отклонять IPv6 сразу, если сервер его не открывает`.
- Заголовок PR выпуска: `Выпуск X.Y.Z: <главное изменение>`.
- Описание заполняется по [шаблону](../.github/PULL_REQUEST_TEMPLATE.md): Изменение,
  Проверка, Риск, Ревью, Откат, Связанные задачи.
- В разделе «Связанные задачи» обязательна строка `Closes #N`, если задача есть.
- Один PR — одна задача.
- PR открывается черновиком. Перевод в «Ready for review» означает, что автор
  выполнил проверки и просит ревью.

## Метки

Статус — ровно одна метка `status:*`. Автоматика ставит её на PR и на задачу из `Closes #N`.

| Состояние | Метка | Кто ставит |
| --- | --- | --- |
| Задача заведена | нет | — |
| Можно брать в работу | `status:ready` | Сопровождающий |
| PR готов к ревью | `status:in-review` | Автоматика |
| Ревью нашло P0/P1 | `status:needs-fix` | Автоматика |
| Раунд без P0/P1 | `status:ready-to-merge` | Автоматика |
| PR слит в `dev` | Задача закрыта, метка статуса снята | Автоматика |

Остальные метки:

- `risk:low`, `risk:medium`, `risk:high` — риск PR по REVIEW.md; ставит ревью.
- `P0`, `P1`, `P2` — приоритет замечаний в задаче на исправления.
- `fix:approved` — сопровождающий подтвердил задачу на исправления; запускает агента.
- `needs-maintainer` — автоматика остановилась и ждёт решения сопровождающего.

## Цикл ревью

1. Сопровождающий переводит PR в «Ready for review» — запускается ревью HEAD. Итог раунда
   публикуется комментарием в PR, исходная задача получает `status:in-review`.
2. Есть подтверждённые P0/P1 — создаётся задача `review-fix`, исходная задача получает
   `status:needs-fix`, PR возвращается в черновик.
3. Сопровождающий ставит `fix:approved` на задачу на исправления — запускается агент,
   исправляет замечания и делает push в ветку PR.
4. После push запускается CI ветки, задача на исправления закрывается, PR переводится
   в «Ready for review» и начинается следующий раунд.
5. Раунд без P0/P1 — исходная задача получает `status:ready-to-merge`. Сливает сопровождающий.
6. Третий раунд с блокерами — автоматика ставит `needs-maintainer` на PR и задачу
   на исправления. Пока метка стоит, `fix:approved` агента не запускает.
7. Если агент не сделал ни одного коммита, задача на исправления остаётся открытой
   и получает `needs-maintainer`.

Для PR с риском `risk:high` автоматическое ревью не заменяет решение сопровождающего:
метка `status:ready-to-merge` означает только отсутствие открытых P0/P1.

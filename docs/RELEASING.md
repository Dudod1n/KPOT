# Подготовка релиза

## Ветки и проверочные сборки

Разработка ведётся в `dev`. Обычные pull request направляйте в эту ветку.
В `main` изменения попадают через отдельный pull request `dev → main`, когда
готовы к выпуску. Прямые изменения в `main` не входят в обычный порядок работы.

Перед PR выполните [независимое ревью](../REVIEW.md), отдельно проверьте
безопасность изменённого кода и закройте подтверждённые замечания. Для установщика,
SSH, сохранения данных и CI требуется решение сопровождающего. Результат ревью
и CI относится к конкретному HEAD; после нового push проверяются новые изменения.

Каждый push в `dev` запускает CI на Windows и Linux. Готовые бинарники и
уведомления о лицензиях доступны в разделе Artifacts соответствующего запуска
[Rust desktop](https://github.com/Dudod1n/KPOT/actions/workflows/rust.yml).
Для скачивания артефактов нужна авторизация на GitHub.

Проверочные сборки используют номер готовящейся версии. Указывайте ветку `dev`
и SHA коммита при их передаче для проверки. До готовности выпуска не создавайте
релизный тег: сборки из `dev` не предлагаются через встроенное обновление.

Порядок выпуска: **dev → PR в main → успешный CI и слияние → тег → черновик
релиза → проверка → публикация**.

## Версия и описание

1. В `dev` обновите `package.version` в `Cargo.toml` до стабильной версии и соответствующую запись `krot` в `Cargo.lock` через Cargo.
2. Перенесите готовые изменения из раздела «Не выпущено» в раздел новой версии в `CHANGELOG.md`. Если такого раздела нет, создайте запись версии сразу.
3. Разделяйте новые возможности, изменения поведения и исправления. Описывайте результат для пользователя и совместимость конфигурации.
4. Выполните проверки из [CONTRIBUTING.md](../CONTRIBUTING.md), откройте PR `dev → main` и дождитесь успешного CI перед слиянием.

Версия стабильного релиза имеет вид `X.Y.Z`. Заголовок записи в журнале:

```md
## 0.5.0 — 2026-10-16

### Добавлено

- Описание новой возможности.

### Исправлено

- Описание ошибки и исправленного поведения.
```

Не включайте пустые разделы. Описание GitHub Release берётся из записи этой версии в `CHANGELOG.md`, до следующего заголовка второго уровня.

## Тег и публикация

После слияния PR дождитесь успешного CI на итоговом коммите `main`.
Создайте аннотированный тег `vX.Y.Z` на этом коммите и отправьте только тег.
Например:

```sh
git switch main
git pull --ff-only origin main
git tag -a v0.5.4 -m 'КРОТ 0.5.4'
git push origin v0.5.4
```

Workflow [Rust release](../.github/workflows/rust-release.yml) проверяет обе платформы, собирает бинарники и создаёт черновик релиза. Проверьте описание, файлы, контрольные суммы и запуск приложения. После одобрения проверки опубликуйте релиз вручную. Повторный запуск сохраняет существующий релиз и его файлы.

Архивы ручной установки содержат окно, CLI, краткую инструкцию, иконки, GPL и уведомления о лицензиях зависимостей. Сборщик [collect_licenses.py](../scripts/collect_licenses.py) подготавливает уведомления для соответствующей платформы из зафиксированных зависимостей. При обновлении зависимостей проверьте их лицензии и уведомления; неизвестное отсутствие текста лицензии останавливает сборку.

Для встроенного обновления требуются отдельные файлы с точными именами:

- `krot-windows-x64.exe`
- `krot-cli-windows-x64.exe`
- `krot-linux-x64`
- `krot-cli-linux-x64`

Пакеты, уведомления и файлы обновления включаются в `SHA256SUMS`. Установщик сверяет бинарники с SHA-256 из метаданных GitHub assets. При добавлении цифровой подписи подписывайте оба Windows-файла до упаковки и расчёта контрольных сумм.

## Проверка результата

После публикации проверьте описание, номер версии, доступность архивов и отдельных файлов. Убедитесь, что GitHub назначил правильный latest-релиз и возвращает SHA-256 для бинарников обновления.

Проверка обновлений в приложении работает без токена и требует публичного репозитория. Для проверки установки используйте предыдущую версию с отдельной тестовой конфигурацией, включая запуск новой версии и сохранность настроек. При переиздании той же версии встроенная проверка не предложит её заново; для исправления выпущенной программы нужен новый номер.

## Регрессия после выпуска

Сохраните сведения о сбое и проверьте способ восстановления, указанный в PR.
Откат исходников оформляйте новым коммитом через PR и CI, без переписывания
истории и выпущенных тегов. Исправленную сборку выпускайте под новым номером.

Возврат к предыдущему номеру версии требует ручной установки: встроенное
обновление предлагает только более новые версии. Перед заменой файлов полностью
остановите КРОТ через пункт «Остановить КРОТ» в трее или меню Q. Без окна используйте
`krot-cli --config <файл> stop` (`krot-cli.exe` на Windows). Сохраните конфигурацию и
хранилище доверенных ключей и проверьте их совместимость с выбранной версией.
Добавьте сценарий регрессии в тесты и уточните правила ревью, если существующие
проверки пропустили причину сбоя.
